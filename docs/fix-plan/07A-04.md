## Root cause
The scan loop treats "record" as an atomic unit and applies all guards between units; a broken file can make one unit take the entire spool and ~2 min of RAM doubling + clone. `QuoteGuard`Type at `scan.rs:375-389` (the reviewer's numbers) is the natural place to track per-field byte budget — the reader already sees every byte.

## Fix (minimal)
1. In `QuoteGuard` (`scan.rs:330-389`): track bytes since the last `FieldStart` (or record break); return an `io::Error` (a `LongField`/`ParseError` row state) past a budget such as `max_field_chars × 4`; also honor `cancel` and the deadline mid-field inside the reader rather than only at loop top.
2. Wire the budget via `QuoteGuard::new` (`scan.rs:155`) reading `request.limits.max_field_chars` (`model.rs:37-70`).
3. Optional (they can be staged): assign the worker to a Job object with `JOB_OBJECT_LIMIT_PROCESS_MEMORY | JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` in the spawner — v1 doc says available; only implement if trivially placed after the budget lands.
- Rejected alternative: relying on the 5 s kill in `finish_child` — 5 s × 4 GiB record is exactly how the system memory-pressure phase unfolds; the budget is the fix.
