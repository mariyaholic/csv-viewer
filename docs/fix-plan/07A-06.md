# csv-viewer 07A-06 — DLL can be unloaded while its own threads still run; window class is registered under the host EXE's HINSTANCE and never unregistered

- Severity: medium
- Pinned SHA verified: `eb3580da4c5820b9ca930c26de9b3f53a4839b2b`
- Status: **CONFIRMED** — `DllCanUnloadNow` (`windows.rs:951-960`) counts only `LIVE_COM_OBJECTS`/`SERVER_LOCKS`; live threads outlive it: waiter thread (`windows.rs:783-786`, posts to a possibly-destroyed HWND), spool/scan/timeout threads (`session.rs:253/323/356`), worker reader thread (`backend.rs:111`), and `finish_child` (`backend.rs:296-316`) which sleeps up to 500 ms. The window class is registered with `hInstance: GetModuleHandleW(ptr::null())` — the host EXE (`windows.rs:599`, `:670` for CreateWindowExW) — and `UnregisterClassW` is never called (grep 0 hits); re-registration failure (`ERROR_CLASS_ALREADY_EXISTS`) is tolerated at `windows.rs:607-614`, so after a reload the pane uses the *previous* mapping's wndproc.
- Helper already exists but is unused for this purpose: `DLL_INSTANCE`/`this_module()` (`windows.rs:897-904`).
- Size: M · Model effort: strong mid-tier
- Depends on: no hard dependency; land alongside 07A-05 (both are lifecycle) and *before* 07A-02's new-thread redesign so new threads pin the module too.
- Manager sign-off: not required.

## Root cause
The unload story tracks COM object lifetimes only, not thread lifetimes; and the window class is registered on the host's image instead of the DLL's image, so after DLL reload the stale class points at old code. The fixer's mirror image: 07b keeps its DLL resident (DllCanUnloadNow never allows), which is the *other* valid strategy — but this repo's contract is lifetimes-aware.

## Fix (minimal)
1. Register the class with `this_module()`/`DLL_INSTANCE` (`windows.rs:590-616`) and call `UnregisterClassW` when the last live object drops (or on DLL_PROCESS_DETACH).
2. Add a static live-thread counter (increment on spawn, decrement at thread exit); include it (and the current SERVER_LOCKS/LIVE_COM_OBJECTS programme) in `DllCanUnloadNow`'s verdict.
3. For the threads that can outlive a `FreeLibrary`: either pin the module (`GetModuleHandleExW(PIN/ FROM_ADDRESS)`) or exit via `FreeLibraryAndExitThread`. Minimum viable: every spawned worker/spool thread holds a non-zero refcount until its last `PostMessageW`/file close — and the unload test below proves it.

## Risk / blast radius

- Risk: over-eager unregistration while another handler instance in the same host still uses the class — the counter must reach zero for *all* objects, not just ours-on.
