# csv-viewer 07A-10 — `WM_DPICHANGED` is never delivered to a child window; the DPI "fix" is inert

- Severity: low
- Pinned SHA verified: `eb3580da4c5820b9ca930c26de9b3f53a4839b2b`
- Status: **CONFIRMED** — `windows.rs:800` handles `WM_SIZE | WM_DPICHANGED =>` on a `WS_CHILD` window (`:663`); Windows sends `WM_DPICHANGED` only to top-level windows; children get `WM_DPICHANGED_AFTERPARENT` (0x02E3), which the repo never mentions (grep 0 hits; the `WM_DPICHANGED` constant itself is at `windows.rs:66`); the font is sized once from LOGPIXELSY at `windows.rs:845` — no `GetDpiForWindow` usage.
- Size: S · Model effort: entry-level
- Depends on: none.
- Manager sign-off: not required.

## Root cause
The DPI handler was written against the top-level message contract while the pane is a child window; the actual message the pane *can* receive (WM_DPICHANGED_AFTERPARENT) is unhandled, so the font never rescales when Explorer moves between monitors.

## Fix (minimal)
- In `preview_window_proc` (`windows.rs:792-831`): add `WM_DPICHANGED_AFTERPARENT (0x02E3)` to the DPI arm and rebuild the font from the current DPI — prefer `GetDpiForWindow` (new extern in the user32 block `windows.rs:1393-1429`) over LOGPIXELSY so per-monitor scaling is honored.
- Keep the existing `WM_DPICHANGED` arm harmless (it simply won't fire; leave for top-level future reuse).

## Acceptance test
- Automated: unit test asserting the font-rebuild helper is invoked when 0x02E3 is delivered — extract `rebuild_font_for_dpi(hwnd)` and fake the call count; fails before (no 0x02E3 arm), passes after.
- Manual on this PC (decisive, XR-2): drag Explorer between a 100% and a 200% monitor; the pane's font must rescale while the pane stays usable.
