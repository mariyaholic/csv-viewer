## Root cause
No self-restraint at the ABI boundary: any future panic (mutex poison, thread-spawn failure, parser or text-render change) escapes an `extern "system"` function, and since Rust 1.81 that aborts the process — which also kills the Explorer host process for all other handlers.

## Fix (minimal)
1. Wrap the body of each exported/vtable function in `std::panic::catch_unwind(AssertUnwindSafe(|| …)).unwrap_or(Err(ffi::E_FAIL))` (or `DefWindowProcW` fallback for the wndproc): export entries (`windows.rs:928` DllGetClassObject, `:954` DllCanUnloadNow, `:963` DllRegisterServer, `:973` DllUnregisterServer), the vtable closure bodies (`windows.rs:291-323` pattern per the COM structs), and the window proc.
2. Replace bare `thread::spawn` with `thread::Builder::spawn` and handle the `Err` (`windows.rs:783`; same for `session.rs:253,323,356` and `backend.rs:111`) — thread-spawn failure becomes an E_FAIL/or-no-op instead of a panic.
- Rejected alternative: global `panic = "abort"`… no — that makes every panic fatal, the opposite direction. Also rejected: changing the Unwinding setting; keep unwind but contain at the boundary.

## Acceptance test
- Name: `panic_in_preview_does_not_abort_host` — debug-gated (config-testable) unit test that calls the wrapped entry (e.g. preview_do_preview seam) with a stub that panics; assert the return value is `E_FAIL` and the process survives (trivially true if the wrapper works — the pre-state is a test that can't return because abort, hence the fails-before attribute).
-Manual on this PC: debug build with an injected panic in `refresh_text` (the finding's verify plan); Explorer stays alive, the pane shows the error text/blank.

## Risk / blast radius
- Broad mechanical change but shallow: each `catch_unwind` site is self-contained. AssertUnwindSafe is fine here only *because* the wrapper's contract pays with an E_FAIL, not state reuse — the fixer must not "restore" state after unwind; just fail the call.
