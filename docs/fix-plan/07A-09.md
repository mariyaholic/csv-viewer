# csv-viewer 07A-09 — A source whose size exactly equals the spool cap is marked truncated (off-by-one)

- Severity: low
- Pinned SHA verified: `eb3580da4c5820b9ca930c26de9b3f53a4839b2b`
- Status: **CONFIRMED** — `session.rs:488-490`: `let allowed = (max_spool - bytes) as usize; if allowed == 0 { truncated = true; break; }` — after the cap, the source is never read again; `copy_owned_source` (`:139`) deliberately copied `limit+1` bytes ("lets the normal spool detect truncation") but the probe was never implemented. ## Root cause
The cap boundary was written as "cap reached ⇒ truncated" instead of "cap reached ⇒ probe whether more bytes exist". The +1 propagation introduced for exactly this probe never got its consumer.

## Fix (minimal)
- In the `allowed == 0` branch: attempt one more read from the source; set `truncated` only if that read returns > 0; update `total_bytes` handling to keep streaming until the +1 source says done.

## Acceptance test
- Name: `spool_exact_cap_is_not_truncated` in `tests/session.rs` (the existing `spool_cap_marks_a_scan_incomplete` at `:65-84` covers the *over*-cap case; complementary): a source of exactly `max_spool_bytes` length with zero extra bytes → `truncated == false` and complete coverage. Also verify the cap+1 source (the real 07A-02 production shape) yields `truncated == true` — that's the probe actually firing.
- Fails before (`truncated == true` for the exact-cap source), passes after.
