## Root cause
Round 3 chose "leave keys, don't race" and left an empty per-user leaf key; the open question is whether the empty HKCU leaf has priority over, or just complements, an installed HKLM handler in Explorer's merged association resolution — and the round acknowledges the uncertainty explicitly.

## Fix (conditional on C1 — deleting the empty leaf mirrors parquet-viewer's policy)
1. Add a `Registry` trait method `delete_key(key: &str)`; implement with `RegDeleteKeyW` in the `advapi32` block (`windows.rs:1458-1496`) + WindowsRegistry impl (`:1164-1177`) + Fake mock; delete the leaf key `{8895…}` unconditionally as removal-of-*our* value-ownership (matching the 07b `delete_tree` policy).
2. Keep deleting *values* as today; only the now-empty leaf key gets removed.
3. Update the residue assertion test (`registration.rs:296-297`) to assert absence post-unregister and presence-restore for the backups path.
- Rejected alternative: racing emptiness-check + delete — the comment 07a itself wrote says non-atomic; delete-only-our-key avoids the race entirely.

## Acceptance test
